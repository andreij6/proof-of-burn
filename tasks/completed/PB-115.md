# PB-115 — Backend: add `get_global_stats` query for TVL / total burned / votes cast

The header stats strip needs a single source of truth for app-wide numbers.
Today the frontend derives per-user stats from `get_my_commitments` and the
per-proposal `total_committed_e8s` from `list_active_proposals`, but neither
gives a clean app-wide number for the new global strip.

## Scope

Add a new query:

```rust
#[derive(CandidType, Serialize, Deserialize, Clone, Debug)]
pub struct GlobalStats {
    pub tvl_e8s: u64,             // sum of total_committed_e8s over open+met proposals
    pub total_burned_e8s: u64,    // sum of icp_burned_e8s over all VoteRecord entries
    pub votes_cast: u64,          // VOTES.len()
}

#[ic_cdk::query]
fn get_global_stats() -> GlobalStats { ... }
```

Computation:
- `tvl_e8s` = `sum(p.total_committed_e8s for p in PROPOSALS if p.status in {"open", "met"})`
  - Use `checked_add` and clamp to `u64::MAX` to keep F-105's overflow posture.
- `total_burned_e8s` = `sum(v.icp_burned_e8s for v in VOTES)`
  - Same overflow handling.
- `votes_cast` = `VOTES.len() as u64`.

This is a pure read over in-memory maps — `O(n)` over proposals + votes. Safe
for any reasonable n; document that the query walks both maps in full.

## Acceptance criteria

- `get_global_stats` is a `query` (not an update) — no state mutation.
- All three fields are non-negative u64s.
- The query is covered by a roundtrip test (`GlobalStats` storable? no — not
  stored, but at least the function compiles and returns the expected shape
  against the seeded mock data).
- `cargo build --release` still passes.
- The `.did` file is regenerated by the build pipeline (icpBindgen) — no
  manual edit needed.

## Notes / pitfalls

- Do NOT sum over `total_burned_e8s` on `Proposal` (it's `Option<u64>` and
  per-proposal; the `VoteRecord` ledger is the canonical burn record).
- `VOTES` is keyed by `proposal_id` — `len()` gives the count of distinct
  proposals voted on, which matches the user-facing metric.
