# PB-111 — Make burn_to_cycles idempotent (fix fund stranding on retry)

**CRITICAL — can permanently strand committed ICP.** `burn_to_cycles` performs two sequential inter-canister calls with no persistence between them.

## Finding F-103
`src/backend/src/lib.rs` (~line 817):
1. `icrc1_transfer` moves the escrowed ICP from the user's subaccount → CMC.
2. `notify_top_up` tells the CMC to mint cycles for that block index.

If step 1 succeeds but step 2 fails (CMC busy, transient reject), `burn_to_cycles` returns `Err`. The commitment is marked `FailedBurn`. On the next timer tick, `retry_failed_settlements` calls `burn_to_cycles` **again**, which attempts a **fresh** `icrc1_transfer` from the now-empty subaccount → fails with `InsufficientFunds` → stays `FailedBurn` forever.

Result: the ICP sits at the CMC, the `block_index` from step 1 is lost, cycles are never minted, and the commitment never settles. The same split-call risk exists in `cycle_topup_check`.

## Scope
- Persist the CMC transfer `block_index` on the `Commitment` (e.g. `cmc_block_index: Option<u64>`) immediately after a successful step-1 transfer.
- Split settlement into two retryable phases:
  - Phase A: if `cmc_block_index` is `None`, do the transfer and store the block index.
  - Phase B: if `cmc_block_index` is `Some`, only call `notify_top_up` (idempotent on the CMC side — `AlreadyNotified` should be treated as success).
- Apply the same pattern to `cycle_topup_check` (store treasury sweep block index in stable state, retry notify separately).
- Treat CMC `NotifyError::AlreadyNotified` and `Refunded` explicitly.

## Acceptance criteria
- A burn where step 1 succeeds and step 2 fails, then is retried, results in `Burned` (cycles minted) with **no second transfer** and no stranded funds.
- Refund path retry remains correct (refund transfer is naturally idempotent via balance check — verify).
- Covered by integration tests simulating a CMC that rejects the first notify (see [[PB-112]]).

## Notes / pitfalls
- Requires a `Commitment` schema change → confirm upgrade persistence ([[PB-091]]) still holds with the new field (Option defaults cleanly).
- The same two-call hazard exists anywhere `transfer + notify_top_up` is paired.
