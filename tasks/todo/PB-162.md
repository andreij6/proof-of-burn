# PB-162 — Backend: round lifecycle, score submission + sanity validation, shot log

The Phase-1 trust model: on-chain tickets + bounded, structurally-validated
submissions with the full shot log persisted. Plan §2, decision #4.

## Backend
- `GOLF_SHOTS` stable map at MemoryId 20, key `(round_id, seq)`, value
  `GolfShot { hole: u8, angle_mrad: i32, power: u16 }` (≤ 108 rows/round).
- `submit_golf_score(round_id, per_hole_strokes: Vec<u8>, shots) -> Result`:
  - round exists, owned by caller, status `Paid`, inside TTL, course
    version matches the pinned one.
  - structural checks: hole count matches config; each hole's strokes in
    `1..=12`; `sum(per_hole) == shots.len()`; shot `hole` fields monotonic
    non-decreasing and per-hole counts consistent; `power <= 1000`.
  - wall-clock bound: `now - started_at ∈ [60 s, TTL]`.
  - flips `Submitted`, stores strokes + shot log, audit `golf_score`.
- `get_my_golf_round()` query (resume support) and round expiry
  (`Paid` + TTL elapsed ⇒ `Expired`, lazily and via sweep).
- `RoundStatus::Voided` variant reserved for PB-169.

## Acceptance Criteria
- [ ] Submitting someone else's round / a Submitted round / an expired
      round all rejected with distinct errors.
- [ ] Each structural-validation rule has a host unit test (happy + reject).
- [ ] Shot log is fully retrievable for any submitted round (needed by
      PB-169); storage bounded per round.
- [ ] Sub-60-second submission rejected (`TOO_FAST`).
