# Canister Architecture

This document defines the internal structure of the **Proof of Burn** canister: its data model, stable storage layout, subaccount derivation scheme, timer design, and interactions with external canisters. This is the primary reference for a developer beginning the technical implementation.

---

## 1. Canister Boundaries

The application is built as a **single canister** deployed on the ICP mainnet. All application logic — proposal tracking, user commitment management, escrow accounting, NNS voting, and burn/refund execution — lives within this one canister.

```
┌─────────────────────────────────────────────────────────────────┐
│                    Proof of Burn Canister                        │
│                                                                 │
│  ┌─────────────┐  ┌─────────────────┐  ┌────────────────────┐  │
│  │  Auth Layer  │  │  Proposal State  │  │  Escrow Accounting │  │
│  │ (II Principal│  │  (proposals,     │  │  (subaccounts,     │  │
│  │  validation) │  │   cutoff timers) │  │   commitments)     │  │
│  └─────────────┘  └─────────────────┘  └────────────────────┘  │
│                                                                 │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │                   External Calls                          │   │
│  │  NNS Governance Canister  │  ICP Ledger Canister          │   │
│  │  rrkah-fqaaa-aaaaa-aaaaq  │  ryjl3-tyaaa-aaaaa-aaaba     │   │
│  └──────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────┘
```

**Why a single canister?**
- Eliminates inter-canister latency and async complexity in the escrow flow
- Simplifies auditing — all logic is in one Wasm module
- Reduces cycles overhead
- Sufficient for the data scale of NNS governance (typically tens of active proposals at any time)

## 2. Stable Data Model

All state is stored in **stable memory** so it survives canister upgrades during development (before black-holing) and is not lost on node reboots.

### 2.1 Core Types

```rust
// --- Identifiers ---
type ProposalId  = u64;   // NNS proposal ID
type NeuronId    = u64;   // NNS neuron ID
type Subaccount  = [u8; 32];

// --- Enums ---
enum Stance {
    Adopt,
    Reject,
}

enum ProposalStatus {
    Open,        // Accepting commitments
    Cutoff,      // 1hr window reached, awaiting execution
    Voted,       // manage_neuron called, burns/refunds in progress
    Settled,     // All burns and refunds complete
    Abstained,   // Threshold not met; refunds complete
}

enum CommitmentStatus {
    Pending,     // Held in escrow, awaiting outcome
    Burned,      // ICP transferred to minting account
    Refunded,    // ICP returned to user
    FailedBurn,  // Burn transfer failed; needs retry
    FailedRefund,// Refund transfer failed; needs retry
}
```

### 2.2 Proposal Record

```rust
struct ProposalRecord {
    nns_proposal_id:    ProposalId,
    title:              String,
    topic:              i32,            // NNS topic integer
    deadline_ns:        u64,            // NNS proposal deadline (nanoseconds since epoch)
    cutoff_ns:          u64,            // deadline_ns - 3_600_000_000_000 (1 hour)
    status:             ProposalStatus,
    adopt_pot_e8s:      u64,            // running total of ADOPT commitments
    reject_pot_e8s:     u64,            // running total of REJECT commitments
    threshold_e8s:      u64,            // default: 25_000_000_000 (250 ICP in e8s)
    vote_executed_at:   Option<u64>,    // timestamp when vote was cast
    total_burned_e8s:   Option<u64>,    // total ICP burned (if threshold met)
}
```

### 2.3 Commitment Record

```rust
struct CommitmentRecord {
    user_principal:          Principal,
    proposal_id:             ProposalId,
    stance:                  Stance,
    target_e8s:              u64,      // conviction amount (burned or refunded)
    protocol_fee_e8s:        u64,      // always 500_000 (0.005 ICP) — non-refundable
    outgoing_fee_reserve_e8s:u64,      // always 10_000 (0.0001 ICP) — for burn/refund tx
    fee_transfer_reserve_e8s:u64,      // always 10_000 (0.0001 ICP) — for fee→treasury tx
    total_deposited_e8s:     u64,      // target + 530_000 (after incoming 10_000 deducted by ledger)
    subaccount:              Subaccount, // unique escrow subaccount
    status:                  CommitmentStatus,
    created_at:              u64,      // timestamp
    settled_at:              Option<u64>, // timestamp of burn or refund
}
// Total user sends: target + 530_000 e8s (= target + 0.0053 ICP)
//   - Ledger deducts 10_000 incoming fee, canister subaccount receives target + 520_000
//   - Canister moves 510_000 (protocol_fee + its transfer fee) to treasury
//   - Subaccount retains: target + 10_000 (outgoing fee reserve)
```

### 2.4 User Neuron Record

```rust
struct UserNeuronRecord {
    user_principal:     Principal,
    neuron_id:          NeuronId,
    is_following:       bool,
    cached_stake_e8s:   u64,           // cached from last get_full_neuron call
    last_verified_at:   u64,           // timestamp of last on-chain verification
}
```

### 2.5 Treasury Subaccount

Protocol fees are collected in a dedicated, well-known subaccount of the canister:

```rust
const TREASURY_SUBACCOUNT: Subaccount = [1u8; 32]; // all bytes = 0x01, distinct from user subaccounts
```

The treasury subaccount accumulates ICP over time. It is publicly visible on the ledger — anyone can verify the protocol fee balance. Its sole purpose is to fund canister cycles via the Cycles Minting Canister (see Section 4.3).


## 3. Subaccount Derivation

Each commitment uses a **unique 32-byte subaccount** derived deterministically from the user's principal and the proposal ID. This ensures:
- Funds are isolated per (user, proposal) pair
- The canister can reconstruct the subaccount at any time without extra state
- Transactions are independently auditable on the ledger

```rust
fn derive_subaccount(user: &Principal, proposal_id: ProposalId) -> Subaccount {
    let mut hasher = Sha256::new();
    hasher.update(b"proof_of_burn_escrow_v1");  // domain separator
    hasher.update(user.as_slice());
    hasher.update(&proposal_id.to_be_bytes());
    let hash = hasher.finalize();
    let mut subaccount = [0u8; 32];
    subaccount.copy_from_slice(&hash);
    subaccount
}
```

The user's deposit address for a given proposal is:
```
AccountIdentifier {
    owner:      PROOF_OF_BURN_CANISTER_PRINCIPAL,
    subaccount: derive_subaccount(user_principal, proposal_id)
}
```

## 4. Timer Design

The canister uses **IC certified timers** (`ic_cdk_timers`) to automate proposal lifecycle transitions. Three timer jobs run:

### 4.1 Proposal Sync Timer (Periodic — every 5 minutes)
- Calls `list_proposals` on the NNS Governance Canister to fetch newly created active proposals.
- For each new proposal not yet in the canister's `proposals` map:
  - Creates a `ProposalRecord` with status `Open`.
  - Schedules a **Cutoff Timer** at `deadline_ns - 1 hour`.
- Updates `deadline_ns` on existing proposals if NNS deadline changes (rare but possible).

### 4.2 Cutoff Timer (Per-Proposal — fires 1 hour before NNS deadline)
- Sets the proposal status to `Cutoff`.
- Closes the commitment window: the canister rejects any further `commit` calls for this proposal.
- Tallies `adopt_pot_e8s` and `reject_pot_e8s`.
- **If threshold met:** Calls `manage_neuron` to register the vote on the NNS. Sets status to `Voted`. Schedules the **Settle Timer**.
- **If threshold not met:** Sets status to `Abstained`. Schedules the **Settle Timer** (for refunds).

### 4.3 Cycle Top-Up Timer (Periodic — every 24 hours, runs within Proposal Sync Timer)
- Queries the canister's own cycle balance via `ic0.canister_cycle_balance()`.
- If cycles < **LOW_WATER_MARK** (5 trillion cycles, ~5T):
  1. Query treasury subaccount balance via `icrc1_balance_of`.
  2. If treasury balance > **MIN_TOPUP_AMOUNT** (10 ICP minimum to justify a conversion call):
     - Transfer treasury ICP to the CMC's designated top-up address, with the canister's own principal as the memo target.
     - Call `notify_top_up` on the CMC (`rkp4c-7iaaa-aaaaa-aaaca-cai`) to trigger the ICP → cycles conversion.
     - CMC credits the resulting cycles directly to the canister balance.
- This runs silently within the existing Proposal Sync Timer loop — no separate timer is needed.

**Sustainability estimate at 250 users:**
| Metric | Value |
|---|---|
| Commitments/year | ~25,000 |
| Protocol fee per commitment | 0.005 ICP |
| Annual fee revenue | ~125 ICP |
| Annual cycle cost | ~77B cycles ≈ 0.077 XDR ≈ $0.10 |
| Fee revenue vs. cost ratio | ~1,000× |
| Cycle runway from first year's fees alone | ~50+ years |

### 4.4 Settle Timer (Per-Proposal — fires immediately after Cutoff Timer completes)
- Iterates over all `CommitmentRecord`s for the proposal via `proposal_commitments` index.
- For each commitment:
  - **If `Voted` (threshold met):** Transfers `target_e8s` from the commitment's subaccount to the ICP minting account. Sets `CommitmentStatus::Burned`.
  - **If `Abstained` (threshold not met):** Transfers `target_e8s` from the subaccount back to `user_principal`. Sets `CommitmentStatus::Refunded`.
  - On failure: Sets status to `FailedBurn` or `FailedRefund` for retry (see Error Handling spec).
- When all commitments are settled: Sets proposal status to `Settled`.

```text
Timeline for a single proposal:

[Open]──────────────────────────[Cutoff -1hr]──[Deadline]
  │  users commit freely           │                │
  │                                │                │
  └── Proposal Sync Timer adds ───►│                │
      proposal to state            │                │
                                   ▼                │
                            Cutoff Timer fires      │
                            Tally pots              │
                            Vote (if threshold met) │
                            Schedule Settle Timer   │
                                   │                │
                                   ▼                │
                            Settle Timer fires      │
                            Burn or Refund all      │
                            commitments             │
```

## 5. Public Canister Interface (Candid)

```candid
service proof_of_burn : {
  // --- Query Methods (read-only, free) ---

  // Returns all active proposals with current pot totals
  get_active_proposals : () -> (vec ProposalView) query;

  // Returns paginated vote history (settled proposals)
  get_vote_history : (offset: nat32, limit: nat32) -> (vec VoteHistoryEntry) query;

  // Returns the caller's neuron registration status
  get_my_neuron_status : () -> (opt UserNeuronView) query;

  // Returns the caller's commitments across all proposals
  get_my_commitments : () -> (vec CommitmentView) query;

  // Returns a single proposal's full detail (including per-user commitment if caller has one)
  get_proposal : (proposal_id: nat64) -> (opt ProposalView) query;

  // Returns the current treasury subaccount ICP balance (public, for transparency)
  get_treasury_balance : () -> (nat64) query;

  // Returns the canister's current cycle balance (public, for transparency)
  get_cycle_balance : () -> (nat64) query;


  // --- Update Methods (state-changing, require II authentication) ---

  // Register and verify a user's neuron (adds canister as hotkey, queries NNS)
  register_neuron : (neuron_id: nat64) -> (Result);

  // Re-verify follow status (user calls after following in NNS Dapp)
  verify_follow : () -> (Result);

  // Returns the deposit address for a given proposal (user sends ICP here)
  get_deposit_address : (proposal_id: nat64) -> (DepositAddress);

  // Finalise a commitment after ICP has been deposited
  commit : (proposal_id: nat64, stance: Stance, target_e8s: nat64) -> (Result);
}
```

## 7. Cycles Budget Consideration

Because the canister is black-holed after launch, it must be funded with enough cycles to run indefinitely without a top-up mechanism.

Estimated ongoing costs:
- **Inter-canister calls** to NNS and Ledger: dominant cost driver
- **Proposal Sync Timer** (every 5 min × ~105,000/year × call cost): estimated ~1–2 XDR/year
- **Storage** (stable memory): minimal for expected proposal/commitment volumes
- **Settle Timer** (per proposal, bulk transfers): proportional to number of commitments

**Recommendation:** Pre-fund the canister with cycles equivalent to 5–10 years of estimated operation before black-holing. The exact amount should be calculated during testnet benchmarking.
