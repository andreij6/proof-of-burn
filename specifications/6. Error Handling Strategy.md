# Error Handling Strategy

This document defines how the Proof of Burn canister detects, responds to, and recovers from failure conditions. Because the canister is immutable after deployment, all error paths must be anticipated and handled correctly in the initial code.

The guiding principle is: **user funds must never be permanently lost due to a technical failure.** Every error either has a retry path or surfaces actionable information to the user.

---

## 1. Failure Categories

| Category | Examples | Fund Risk? |
|---|---|---|
| **User Input Errors** | Commitment below minimum, already committed | No |
| **Precondition Failures** | Not authenticated, not following neuron | No |
| **Ledger Transfer Failures** | ICRC-1 transfer returns `Err`, network timeout | Yes |
| **NNS Call Failures** | `manage_neuron` rejected, `get_full_neuron` timeout | Indirect |
| **Timer Misfires** | Cutoff timer fires late or not at all | Yes |
| **Cycles Exhaustion** | Canister runs out of cycles | Yes (catastrophic) |

---

## 2. User Input and Precondition Errors

These are the simplest category — the canister rejects the call before any state is changed or funds are touched.

| Error | Canister Response | User-Facing Message |
|---|---|---|
| Not authenticated (anonymous principal) | Return `Err("NOT_AUTHENTICATED")` | "Please sign in with Internet Identity to continue." |
| Neuron not registered | Return `Err("NEURON_NOT_REGISTERED")` | "Please register and verify your neuron first." |
| Neuron not following leader | Return `Err("NOT_FOLLOWING")` | "Your neuron is not yet following the Leader Neuron. Complete setup in the NNS Dapp." |
| Already committed to this proposal | Return `Err("ALREADY_COMMITTED")` | "You have already committed to this proposal. Commitments are final and cannot be repeated." |
| Commitment below 1 ICP minimum | Return `Err("BELOW_MINIMUM")` | "Minimum commitment is 1.0 ICP." |
| Commitment exceeds staked balance | Return `Err("EXCEEDS_STAKE_CAP")` | "Your commitment cannot exceed your staked neuron balance of X ICP." |
| Proposal is past cutoff | Return `Err("COMMITMENT_CLOSED")` | "This proposal's commitment window has closed." |
| Proposal not found | Return `Err("PROPOSAL_NOT_FOUND")` | "This proposal is not active or does not exist." |

All `Err` variants are returned synchronously before any ledger interaction. The frontend maps error codes to human-readable messages.

---

## 3. Deposit Verification (Commit Flow)

The commit flow involves two steps: the user deposits ICP to their subaccount, then calls `commit()`. The canister verifies the deposit before finalising the commitment.

### Failure: Deposit Not Received
- **Cause:** User calls `commit()` before their ICP transfer has been confirmed on the ledger.
- **Canister response:** Queries the ledger for the subaccount balance. If `balance < target_e8s + 520_000`, return `Err("DEPOSIT_NOT_FOUND")`.
- **User-facing message:** "Your ICP deposit hasn't been confirmed yet. Wait a few seconds and try again."
- **Retry:** User can call `commit()` again — the canister will re-check the balance each time.

### Failure: Deposit Insufficient
- **Cause:** User sent less than `target + 0.0053` ICP (full deposit including protocol fee and ledger fees).
- **Canister response:** Return `Err("INSUFFICIENT_DEPOSIT")` with the actual balance and the required amount.
- **User-facing message:** "Your deposit of X ICP is insufficient. Required: Y ICP (includes 0.005 ICP protocol fee and 0.0003 ICP in ledger fees). The shortfall remains in your escrow subaccount — you may top up and try again."
- **Recovery:** The user can send the remaining amount to the same subaccount and call `commit()` again.

### Failure: Deposit Surplus
- **Cause:** User sent more than `target + 0.0002` ICP.
- **Canister response:** Accept the commitment using exactly `target_e8s` and `20_000` fee reserve. **Return the surplus** to the user's principal via a ledger transfer immediately during the `commit()` call.
- If the surplus return transfer fails, record the surplus in a `pending_refunds` map and include it in the next Settle Timer sweep.

## 4. Ledger Transfer Failures (Settle Phase)

This is the highest-risk category: the proposal has already been voted on (or abstained), and the canister is executing burns or refunds. A ledger failure here means user funds remain trapped in the escrow subaccount.

### Strategy: Mark-and-Retry with Idempotency

The Settle Timer processes each commitment individually. If a transfer fails:
1. The `CommitmentStatus` is set to `FailedBurn` or `FailedRefund`.
2. The commitment is added to a `retry_queue: Vec<(Principal, ProposalId)>`.
3. A **Retry Timer** is scheduled to fire after 60 seconds.

The Retry Timer re-attempts all `FailedBurn` and `FailedRefund` commitments. Retries use the same subaccount and target amount — the transfer is **idempotent by design** because the subaccount balance determines what can be sent.

### Retry Backoff Schedule

| Attempt | Delay |
|---|---|
| 1st retry | 60 seconds |
| 2nd retry | 5 minutes |
| 3rd retry | 30 minutes |
| 4th+ retry | 6 hours |

After **10 failed attempts**, the commitment is flagged as `StuckFunds`. It remains in the stuck queue indefinitely and is publicly queryable via `get_stuck_funds()`. Because the canister is immutable, **stuck funds can only be resolved by the affected user contacting the ICP community** — this is an explicit, accepted trade-off of the immutability design. The subaccount balance is always publicly visible on the ledger, providing an on-chain audit trail.

### Failure: Transfer Returns `Err` (e.g., `InsufficientFunds`, `BadFee`)

| ICRC-1 Error | Interpretation | Action |
|---|---|---|
| `InsufficientFunds` | Fee reserve was consumed (edge case) | Flag as `StuckFunds` immediately — no recovery without upgrade |
| `BadFee` | Ledger fee changed after deployment | Flag as `StuckFunds` — this is a protocol-level change |
| `TooOld` / `CreatedInFuture` | Timestamp drift | Retry with corrected timestamp |
| `Duplicate` | Transfer already processed | Treat as success — mark as Burned/Refunded |
| Generic trap / timeout | Transient network issue | Retry per backoff schedule |

### The `Duplicate` Case (Idempotency)
If the canister successfully submits a transfer but does not receive the response (e.g., due to a message drop), a retry would attempt the same transfer again. The ICRC-1 ledger returns `Err(Duplicate { duplicate_of: BlockIndex })` in this case. The canister must treat `Duplicate` as a **success** and set the commitment status to `Burned` or `Refunded` accordingly.

## 5. NNS Call Failures (Vote Execution)

The Cutoff Timer calls `manage_neuron` to register the Leader Neuron's vote.

### Failure: `manage_neuron` Returns Error or Times Out

| Scenario | Action |
|---|---|
| NNS returns a rejection (e.g., proposal already expired) | Log the error. Set proposal status to `VoteFailed`. Treat as threshold-not-met: schedule refunds for all commitments. |
| Canister does not receive a response (timeout / dropped message) | Schedule a **Vote Retry Timer** at +5 minutes. Re-check proposal status on NNS first (`get_proposal`). If proposal is still open, retry `manage_neuron`. If already voted or expired, proceed accordingly. |
| NNS proposal deadline has already passed when timer fires | The proposal can no longer be voted on. Set status to `VoteFailed`. Refund all commitments. |

**Important:** The canister must check NNS proposal status before retrying a vote — it must never attempt to vote on an already-closed proposal.

## 6. Timer Reliability

IC timers are best-effort and may fire late. The canister design must be resilient to this.

### Cutoff Timer Fires Late
- **Scenario:** The cutoff timer fires after the 1-hour window but before the NNS deadline.
- **Mitigation:** The timer checks `current_time < proposal.deadline_ns` before calling `manage_neuron`. If still within the deadline, proceed normally. If past the deadline, treat as `VoteFailed` and schedule refunds.

### Cutoff Timer Does Not Fire
- **Scenario:** A timer is lost (e.g., canister was briefly unresponsive during a subnet upgrade).
- **Mitigation:** The Proposal Sync Timer (every 5 minutes) checks all `Open` proposals. For any proposal where `current_time >= cutoff_ns` and status is still `Open`, it manually triggers the cutoff logic. This acts as a watchdog.

### Settle Timer Does Not Fire
- **Mitigation:** Same watchdog pattern — the Proposal Sync Timer checks for `Voted` or `Abstained` proposals that have no associated `FailedBurn`/`FailedRefund` records but also have uncommitted commitments. If found, it re-triggers the Settle Timer.

## 7. Cycles Exhaustion

This is the most catastrophic failure mode. If the canister runs out of cycles, it is deleted by the IC — and all escrow funds become permanently inaccessible.

### Prevention
- **Pre-fund generously:** Calculate 10 years of operating costs during testnet and fund accordingly before black-holing (see Canister Architecture spec, Section 7).
- **Cycles monitoring:** Before black-holing, verify the canister balance via `canister_status`. Publish the balance publicly.
- **Accept cycles from any caller:** The canister should implement `wallet_receive()` to accept cycle top-ups from external wallets even after black-holing. This provides a community-run "keep alive" safety net. Note: accepting cycles does not constitute an upgrade or governance action.

### If Cycles Are Depleted
There is no automated recovery path once the canister is black-holed. This outcome is disclosed to users as an accepted systemic risk in the app's transparency documentation.

---

## 8. Error Surface: Frontend Responsibilities

The frontend is responsible for:
1. Mapping canister error codes (e.g., `ALREADY_COMMITTED`) to friendly UI messages.
2. Displaying commitment status badges that reflect `FailedBurn` / `FailedRefund` / `StuckFunds` states clearly.
3. Surfacing the `get_stuck_funds()` endpoint in a publicly visible "System Health" section so the community can see if any funds are unresolved.
4. Showing the canister's cycle balance in the footer or system info section (queryable via management canister `canister_status`).
